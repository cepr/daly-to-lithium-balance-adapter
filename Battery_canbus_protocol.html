Messages received by the BMCU

ID (hex)Interval (ms)Signals
0x10A—2072: unnamed value; × 10 is forwarded in 0x2FF
0x119—2043: SoC set command (also sent back in 0x204)
0x605—2122: contactor-open request, with timeout

ID 0x10A — received

Start bitBit countData identifierByte countIntel format
56820722No

From the firmware (6.18.0): the BMCU stores byte 7 of the frame as data identifier 2072 and nothing else in the firmware reads it by name. It is only used by the post processor (rows 1 and 2): row 2 multiplies it by 10 and sends the result in 0x2FF as Post_Processor_1. Its meaning has to come from the sender of 0x10A.

ID 0x119 — received

Start bitBit countData identifierByte countIntel format
0820431No

From the firmware (6.18.0): SoC set command. Byte 0 is a state of charge in %. When a frame arrives and the value is below 100, the BMCU overwrites its SoC (data identifier 2021, sent in 0x200) with it and recalculates the remaining charge from the capacity setting. It then ignores further SoC commands for about 25 s (a 250-count timer decremented every 100 ms). Values of 100 or more are ignored. The last received value is sent back out in 0x204 bits 40–47.

ID 0x605 — received

Start bitBit countData identifierByte countIntel format
56821221No

From the firmware (6.18.0): contactor-open request. While 2122 is non-zero, the BMCU's contactor logic switches off both contactor outputs (PORTD bits 1 and 2, the precharge and main drive pins) and goes to its open state; while it is zero, the BMCU may close them as usual. Each frame with a non-zero byte 7 restarts a timeout: the BMCU loads a counter from configuration parameter 559 (in 100 ms steps, minimum 3 = 300 ms). If no new non-zero frame arrives before it runs out, the BMCU sets 2122 back to 0 by itself. So the sender must repeat the request to keep the contactors open.

Post processor

BMCU config section; its purpose is not yet confirmed. Row 3 is disabled but has non-default values, so it is shown in grey. Rows 4–8 are disabled placeholders and omitted.

From the firmware (6.18.0), routine at 0xB16C: the post processor runs up to 23 rows in order. Each row computes Operand 1 <operator> Operand 2, where "Direct" reads a data identifier and "Constant" is a literal, and writes the result to a data identifier, not to a pin: OutputN is data identifier 2070 + 2 × (N − 1), so Output1 = 2070, Output2 = 2072, Output3 = 2074 (up to Output20 = 2108).

  • Row 1: [2072] = [2072] AND 0xFF. It writes back into 2072 itself, keeping only the low byte of the value received in 0x10A.
  • Row 2: [2070] = 10 × [2072]. Data identifier 2070 is the Post_Processor_1 signal sent in 0x2FF bits 8–17.
  • Row 3 (disabled): [2074] = [2016] ÷ 256.

So byte 7 of 0x10A, multiplied by 10, is forwarded in the charger message 0x2FF. The s-BMS User Manual v2.01 (§5.8.6) also calls the B-J3 pins IO 6/7/8 "User selectable output 1/2/3", but the post processor does not drive them: the firmware sets those pins from separate on/off flags, and no code reads data identifiers 2070–2074 except through the generic CAN/post-processor tables. Identifier 2016 appears as a constant in 0x202.
